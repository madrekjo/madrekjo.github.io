## 📅 السجل الزمني

### 2026-09-29 (قسم «اكتب سؤالك» — الإجابة تطلع أخيراً) — v1.6.0

**المشكلة:** الطالب يضغط على خيار… ولا يطلع أي شي. ما في "صحي" ولا "غلط" ولا رسالة خطأ.

**سببين حقيقيين، واحد ورا التاني:**

**1) السبب الجذري — دالة مفقودة بالقاعدة**

`handleAnswer` كان يسلّم الإجابة لدالة `submit_answer` بالخادم عشان يفحص صحتها. لكن الدالة **ما كانت موجودة** أصلاً بالقاعدة:

```
404 PGRST202 — Could not find the function public.submit_answer(p_chosen, p_question_id, p_user_id)
```

المهاجرة `20260918000001_hide_correct_answer.sql` كانت مكتوبة بالمستودع بس **ما نُفِّذت** بلوحة Supabase. والشفرة كانت بتبلع الخطأ وترجع بصمت:

```ts
} catch (e) {
  console.error("[Answer] فشل فحص الإجابة", e);
  return;   // ← ما في أي رد للطالب
}
```

فكل ضغطة كانت بتختفي بلا أثر.

**2) السبب الثاني — حتى بعد ما اشتغلت الدالة، الطالب ما كان بيشوف الإجابة**

الشريط القديم كان بيقول:

```
✕ إجابتك خاطئة — الصحيح: ب
```

حرف واحد. الطالب لازم يرجع يدوّر على الخيار «ب» بنفسه.

**اللي صار:**

| قبل | بعد |
| --- | --- |
| `✕ إجابتك خاطئة — الصحيح: ب` | صندوق أخضر: `✕ إجابتك خاطئة` + `[د] 10` بنص الإجابة الصحيحة |
| الخيار الصحيح بلون خفيف | الخيار الصحيح بإطار أخضر + علامة ✓ خضرا |
| صمت أثناء الفحص | `جاري فحص إجابتك…` + قفل الخيارات (يمنع الضغط المزدوج) |
| `الصحيح: -` عند تعذّر الفحص | `⚠️ ما قدرنا نتحقق من الإجابة` + زر إعادة |

**الحالات الثلاث بعد التعديل:**

| الحالة | العرض |
| --- | --- |
| إجابة صحيحة | `✓ إجابتك صحيحة` |
| إجابة خاطئة | `✕ إجابتك خاطئة` + صندوق أخضر بنص الإجابة الصحيحة + ✓ على الخيار الصحيح |
| تعذّر الفحص | `⚠️ ما قدرنا نتحقق من الإجابة` (بدل ادّعاء أن الإجابة خاطئة) |

**الأمان — S5 (عزل الإجابة الصحيحة):**

الفحص النهائي صار **خادمي بالكامل** عبر `submit_answer` (‏`SECURITY DEFINER`). المتصفح ما عاد يقرأ `correct` أبداً.

⚠️ **متبقي خطوة يدوية:** مهاجرة `20260929000002_lock_correct_column.sql` — لأن `submit_answer` وحدها ما كانت كافية؛ صلاحيات القراءة الافتراضية على الجدول كانت مفتوحة، فأي زائر كان يقدر يقرأ الإجابات قبل الإجابة عبر طلب REST مباشر (`GET /rest/v1/questions?select=id,correct`). الملف يسحب صلاحية `SELECT` عن الجدول ويعيد منح كل الأعمدة عدا `correct`.

**اختُبر فعلياً** بالمتصفح على قاعدة البيانات الحيّة: إجابة خاطئة ← `د — 10`، إجابة صحيحة ← `✓ إجابتك صحيحة`، إعادة الحل ← ترجع للحالة الأصلية.

**النشر:** `ask/` مبني، ورابط الحقول الخمسة `?v=5`.

### 2026-09-29 (إعادة بناء نظام الجولات — النقاط صارت حقيقية) — v1.5.0

**خلفية المشكلة:** نظام الجولات (الجولات/التحدي) كان يعطي النقاط **عشوائياً**. المستخدم بيبدأ جولة وبيحصل على نقاط ما لها أي علاقة بالوقت اللي قعده فيه. وبالأسوأ، كان يقدر يتلاعب بالنتائج من المتصفح.

**المبدأ الأساسي الجديد:** الخادم هو صاحب الوقت والحضور والمال. المتصفح بس يقول "أنا هون والتاب ظاهر" — وما بيقدر يملي على الخادم أي رقم.

**القواعد الجديدة:**
| القاعدة | القيمة |
| --- | --- |
| نبضة الحضور | كل 30 ثانية، بإرجاع من الخادم (`now()`) |
| حد أقصى لكل نبضة | 120 ثانية (يمنع تلاعب الساعة) |
| انقطاع الحضور | فجوة أكبر من 300 ثانية = صفر (يمنعLeaving والرجوع) |
| نقطة واحدة | كل 1200 ثانية (20 دقيقة) تركيز فعلي |
| سقف الرصيد | 50 – 100 |
| مدة العمل | صافي وقت العمل فقط — الاستراحات تُضاف فوقها ولا تُحتسب عملاً |

مثال: جولة 60 دقيقة مع استراحة 5 كل 25 ⇒ **60 دقيقة عمل** + استراحات فوقها (≈70 دقيقة زمن فعلي).

**الأخطاء التسعة التي كانت موجودة:**
1. النقاط كانت تُمنح بمحضrowser clock — أي تعديل على ساعة الجهاز كان يغيّر النتيجة.
2. كان في **مسارَين** للمكافأة (تلقائي + يدوي) ⇒ نقاط مضاعفة.
3. `duration_minutes` كانت تُحسب كـ "باقي المقطع الحالي" أحياناً وإجمالي أحياناً — تعريفان مختلفان لنفس العمود.
4. أول `breakDur` دقيقة من كل فترة كانت تُحسب استراحة **وتُحتسب عملاً في نفس الوقت**.
5. `reward_round_time` كان يتطلب عضوية في `round_participants`، لكن **صاحب الجولة لا يُضاف هناك تلقائياً** — فكان يستحق النقاط فقط من لم ينضم لنفسه.
6. التجديد اليومي كان بعد **23 ساعة** ⇒ "اليوم" صار 23 ساعة، وبلا سطر في السجل ⇒ رصيد المستخدم يختفي بلا تفسير.
7. آخر جزء من النافذة قبل نهاية الجولة كان **يُهمَل** (حتى 120 ثانية لكل جولة تضيع).
8. `guard_round_timing` كان بدون `SECURITY DEFINER` ⇒ كان يفشل صامتاً.
9. `work_remaining` كان يعني "باقي المقطع الحالي" أثناء العمل، وبما يcompatible مع "الإجمالي المتبقي" وقت الاستراحة.

**الحل التقني:**
- جدولان جديدان: `round_presence` (سجل التركيز) و `round_settlements` (النتائج المجمّدة).
- `study_rounds` أُضيف له `scheduled_end_at` و `settled`.
- النقاط تُمنح **تدريجياً** عبر النبضة، والتسوية (settlement) تجمّد السجل فقط ⇒ **لا يوجد مسار لمضاعفة النقاط**.
- حُذف من الكود `rewardRound` و `rewardRoundTime` و `lastRewardedRoundAt` ⇒ استحالة بنيوية لمسار ثانٍ.
- `round_apply_daily_reset(uuid)` دالة مشتركة بين القراءة والنبضة (26 ساعة ⇒ 24 ساعة + تسجيل سطر `daily_reset`).
- `Rounds.tsx` أُعيد كتابته بالكامل، وكل المؤقتات صارت تعتمد على `roundStateAt` (السيرفر).

**الملفات:**
- `chat/supabase/migrations/20260929000001_rounds_real_scoring.sql` — محرّك الخادم (17 دالة، جدولان)
- `chat/src/lib/roundSchedule.ts` — نسخة مطابقة لحسابات SQL
- `chat/src/test/roundSchedule.test.ts` — 23 اختبار يثبّت تطابق TypeScript مع SQL
- `chat/src/pages/Rounds.tsx` — عميل جديد بالكامل
- `chat/src/hooks/useRoundHeartbeat.ts` — نبضة 30 ثانية مربوطة بظهور التاب

**إصلاح إضافي (بعد التشغيل الأول):** أول تشغيل للـ migration أنشأ الدوال لكن-three منها (`start_round` و `round_heartbeat` و `get_user_points`) كانت ترجع نوع بيانات خاطئ. السبب: `NULL` بدون تحديد النوع يُحسبه Postgres `text` بينما الدالة معلنة `timestamptz` أو `integer`. الحل: `NULL::timestamptz` بدل `NULL` في 8 مواضع. تم التحقق بعدها: الـ 6 دوال كلها ترجع HTTP 200 بشكل صحيح.

**ت仄حقق:** 30/30 اختبار ناجح · `tsc --noEmit` نظيف · البناء منشور على `origin/main`.

### 2026-09-03 (نقل قاعدة الدردشة + إصلاح مزامنة الحساب بين القسمين)

**خلفية المشكلة:** كانت الدردشة تعمل على قاعدة Supabase **قديمة** (`ofltanaffcxoobfvlkii`) بينما أقسام أخرى (الإنجاز) على قاعدة مستقلة. قرّرنا **نقل الدردشة إلى قاعدة جديدة** (`biabdoatwfteqwgjdxzc`) ببنية أوضح، مع نظام مزامنة حساب واحد عبر SSO (تسجيل دخول Google) يعمل على القسمين معاً.

**تحديد مراجع المشاريع (مهم للفهم):**
- `itflhfhsfzrdfpxvlzrv` = مشروع **الإنجاز** (قاعدة البيانات والشهادات) — لم يتغيّر
- `biabdoatwfteqwgjdxzc` = مشروع **الدردشة** (القاعدة الجديدة المنقول إليها)
- `ofltanaffcxoobfvlkii` = مشروع **الدردشة القديمة** (المُهجور/المنقول منه)

**المشكلة الأولى — الدردشة لا تعمل بعد النقل:**
- **الأعراض**: بعد تحديث إعدادات الدردشة للقاعدة الجديدة كانت المزامنة تفشل برسالة خطأ 401 (توكين غير صالح) ولا يتم إنشاء حساب الدردشة أو ربط البريد.
- **السبب الجذري**: دالتا الحافة (Edge Functions) `sync-chat-user` (لفحص توكين الإنجاز) و`sync-achievement-user` (لفحص توكين الدردشة) كانتا تتحققان من التوكين الشقيق **بدون ترويسة `apikey`**. نقطة نهاية المصادقة في Supabase تطلب الترويسات `Authorization` و`apikey` معاً، فكا ن التحقق يفشل دائماً.
- **سبب إضافي**: في `sync-achievement-user` كانت `CHAT_AUTH_BASE` تشير إلى القاعدة القديمة `ofltanaffcxoobfvlkii` بدل الجديدة `biabdoatwfteqwgjdxzc`.
- **الحل**: إضافة ترويسة `apikey` الصحيحة في الدالتين + تصحيح `CHAT_AUTH_BASE` إلى القاعدة الجديدة + تعطيل خيار "Verify JWT" على الدالة للسماح بتنفيذ الكود.

**المشكلة الثانية — SSO أحادي الاتجاه:**
- **الأعراض**: تسجيل الدخول من الدردشة → الإنجاز متزامن تلقائياً، لكن من الإنجاز → الدردشة كان يعرض شاشة الدخول بدل المزامنة التلقائية.
- **السبب**: عدم وجود كشف تلقائي موثوق لجلسة القسم الشقيق من جهة الدردشة.
- **الحل**: معالجة في `detectSiblingSync` داخل `chat/src/contexts/AuthContext.tsx`.

**المشكلة الثالثة — Dialog المزامنة لا يختفي ويتكرر:**
- **الأعراض**: كل مرة يُفتح فيها قسم الدردشة تظهر رسالة "مزامنة الحساب — هل تريد استخدام نفس الحساب في الدردشة؟" حتى لو كان المستخدم مسجلاً دخوله بالدردشة أصلاً؛ وعند الضغط على "نعم، مزامنة الحساب" يحمل الزر ولا يختفي Dialog، وعند إعادة الدخول يظهر مجدداً.
- **السبب الجذري**:
  1. `detectSiblingSync` كان يبدأ فوراً بالتوازي مع `INITIAL_SESSION` قبل تحميل جلسة الدردشة من `localStorage`، فكان `getSession()` يعيد `null` فلا يُمنع عرض Dialog.
  2. استخدام `getSession()` في بداية الفحص قد يفشل بسبب تعارض قفل gotrue وقت التهيئة.
  3. `syncWithAchievement` لم يكن يمسح `siblingSync` صراحةً عند نجاح المزامنة — فقط كان يعتمد على حدث `SIGNED_IN` المتأخر.
- **الحل** (في `chat/src/contexts/AuthContext.tsx`):
  - `detectSiblingSync`: استبدال `getSession()` بـ `supabase.auth.getUser()` الذي يتحقق من صلاحية الجلسة الفعلية — إذا المستخدم مسجّل بالدردشة يرجع مبكراً ولا يعرض Dialog.
  - `initializeAuth`: تأجيل فحص المزامنة الشقيقة بـ `setTimeout(1200ms)` حتى يكتمل `INITIAL_SESSION` أولاً.
  - `syncWithAchievement`: إضافة `dismissSiblingSync()` صراحةً عند النجاح ليُغلق Dialog فوراً مهما تأخر الحدث.

**تعديلات مرافقة بعد النقل:**
- `chat/supabase/config.toml`: تصحيح `project_id` إلى `biabdoatwfteqwgjdxzc`.
- `chat/supabase/.temp/linked-project.json` + `supabase/.temp/linked-project.json`: تحديث مرجع المشروع.
- `backup.sh`: تحديث `SUPABASE_URL` إلى القاعدة الجديدة.
- إعادة بناء الدردشة (build جديد) + الرفع على GitHub مع التوثيق.

### 2026-09-01 (نظام أكواد الدعوة + إصلاح "خطأ غير متوقع" + تسجيل الدخول بالإيميل — v1.4.0)

1. **نظام أكواد الدعوة (رمز دعوة من 6 أرقام)** — يتيح للطلاب الذين لا يملكون حساب Google إنشاء حساب :
   - جدول `access_codes` (رمز، حالة، صالح حتى، عدد الاستخدامات، الاسم/وصف يعني للتعليمات)
   - دوال قاعدة بيانات: `create_access_code`، `revoke_access_code`، `list_access_codes`، `validate_access_code`، `consume_access_code`، `refund_access_code` (المحاولات تستهلك الرمز وتُرجَع عند الفشل)
   - دالة سحابية `invite-signup` تُنشئ الحساب وتستهلك الرمز مع فحص الجنس `gender_required`
   - واجهة إدخال الرمز في صفحة الدخول + لوحة إدارة الأكواد (إنشاء/إلغاء/حالة الرمز) في لوحة الأدمن
   - تمييز مستخدم الرمز للأدمن: عمود `via_invite` على `profiles` + إلزام تحديد الجنس عند الحساب الجديد ولاحقاً عبر `GenderOnboardingDialog`، وتحديث trigger `handle_new_user` لملء الحقول تلقائياً

2. **أهم مشكلة حُلَّت (حدث خطأ غير متوقع):**
   - **الأعراض**: عند إدخال رمز الدعوة وبيانات المستخدم تظهر رسالة "خطأ غير متوقع" **مع أن الحساب يُنشأ فعلاً في القاعدة**
   - **السبب الجذري (بعد تتبُّع كامل)**: الدالة السحابية `invite-signup` كانت تُرجع ردها **بدون ترويسة `Content-Type: application/json`**، فتتعامل مكتبة `supabase-js` مع الرد كنص (string) بدل كائن، فيفشل فحص `data.ok` في الواجهة وتظهر الرسالة العامة حتى مع نجاح الإنشاء
   - **الحل**: إضافة الترويسة `Content-Type: application/json` لكل استجابات الدالة + معالجة دفاعية في الواجهة (تحويل النص إلى JSON تلقائياً) — أصبحت العملية تنجح وتدخل تلقائياً دون أي رسالة خطأ

3. **تحسينات مصاحبة:**
   - مهلة أطول لطلبات التغيير (POST) من 15 ثانية إلى **60 ثانية** — لأن طلبات POST لا يعاد إرسالها تلقائياً (غير آمنة) فتحتاج مهلة كافية

   - إصلاح `refund_access_code` داخل الدالة: كان يستخدم `.catch()` على كائن `rpc()` (وله واجهة .then فقط وليس Promise حقيقي) → كان يسبب أخطاء `TypeError` عند تكرار الإيميل → أصبح `async/await` آمن

4. **إضافة تسجيل الدخول بإيميل وكلمة مرور:**
   - تبويب جديد في صفحة الدخول **"تسجيل الدخول بإيميل"** إلى جانب Google ورمز الدعوة
   - مستخدمو رمز الدعوة يحددون إيميلهم وكلمة مرورهم عند الإنشاء، وبعد الخروج يعودون عبر الإيميل مباشرة **دون رمز جديد ودون فقدان حسابهم**
   - استخدام `signInWithPassword` من Supabase Auth

5. **إصلاح Service Worker (SPA):**
