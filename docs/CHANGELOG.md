## 📅 السجل الزمني

### 2026-09-01 (نظام أكواد الدعوة + إصلاح "خطأ غير متوقع" + تسجيل الدخول بالإيميل — v1.4.0)

**الجديد في هذه الجلسة:**

1. **نظام أكواد الدعوة (رمز دعوة من 6 أرقام)** — يتيح للطلاب الذين لا يملكون حساب Google إنشاء حساب :
   - جدول `access_codes` (رمز، حالة، صالح حتى، عدد الاستخدامات، الاسم/وصف يعني للتعليمات)
   - دوال قاعدة بيانات: `create_access_code`، `revoke_access_code`، `list_access_codes`، `validate_access_code`، `consume_access_code`، `refund_access_code` (المحاولات تستهلك الرمز وتُرجَع عند الفشل)
   - دالة سحابية `invite-signup` تُنشئ الحساب وتستهلك الرمز مع فحص الجنس `gender_required`
   - واجهة إدخال الرمز في صفحة الدخول + لوحة إدارة الأكواد (إنشاء/إلغاء/حالة الرمز) في لوحة الأدمن
   - تمييز مستخدم الرمز للأدمن: عمود `via_invite` على `profiles` + إلزام تحديد الجنس عند الحساب الجديد ولاحقاً عبر `GenderOnboardingDialog`، وتحديث trigger `handle_new_user` لملء الحقول تلقائياً

2. **أهم مشكلة حُلَّت (حدث خطأ غير متوقع):**
   - **الأعراض**: عند إدخال رمز الدعوة وبيانات المستخدم تظهر رسالة "خطأ غير متوقع" **مع أن الحساب يُنشأ فعلاً في القاعدة**
   - **السبب الجذري (بعد تتبُّع كامل)**: الدالة السحابية `invite-signup` كانت تُرجع ردها **بدون ترويسة `Content-Type: application/json`**، فتتعامل مكتبة `supabase-js` مع الرد كنص (string) بدل كائن، فيفشل فحص `data.ok` في الواجهة وتظهر الرسالة العامة حتى مع نجاح الإنشاء
   - **الحل**: إضافة الترويسة `Content-Type: application/json` لكل استجابات الدالة + معالجة دفاعية في الواجهة (تحويل النص إلى JSON تلقائياً) — أصبحت العملية تنجح وتدخل تلقائياً دون أي رسالة خطأ

3. **تحسينات مصاحبة:**
   - مهلة أطول لطلبات التغيير (POST) من 15 ثانية إلى **60 ثانية** — لأن طلبات POST لا يعاد إرسالها تلقائياً (غير آمنة) فتحتاج مهلة كافية
   - حذف فحص `listUsers` البطيء (صفحة كاملة + 1000 مستخدم) من الدالة السحابية — اعتمدنا على منع التكرار الذرّي لعملية إنشاء المستخدم، وإصدار خطأ `email_exists` (رمز 409) عند التكرار مباشرة
   - إصلاح `refund_access_code` داخل الدالة: كان يستخدم `.catch()` على كائن `rpc()` (وله واجهة .then فقط وليس Promise حقيقي) → كان يسبب أخطاء `TypeError` عند تكرار الإيميل → أصبح `async/await` آمن

4. **إضافة تسجيل الدخول بإيميل وكلمة مرور:**
   - تبويب جديد في صفحة الدخول **"تسجيل الدخول بإيميل"** إلى جانب Google ورمز الدعوة
   - مستخدمو رمز الدعوة يحددون إيميلهم وكلمة مرورهم عند الإنشاء، وبعد الخروج يعودون عبر الإيميل مباشرة **دون رمز جديد ودون فقدان حسابهم**
   - استخدام `signInWithPassword` من Supabase Auth

5. **إصلاح Service Worker (SPA):**
   - `sw.js` v23: توجيه مسارات `/chat/*` الداخلية إلى `index.html` حتى لا يُرجع نسخاً قديمة/404 بعد كل تحديث
   - `sw.js` v24: تحديث اسم الكاش لكل بناء جديد

**التحقق:** اختبار رحلة كاملة عبر مكتبة supabase-js الحقيقية — التحقق من الرمز (مع رسالته وعدد الاستخدامات) → إنشاء الحساب → الدخول الفوري → قراءة `profiles` (`full_name`، `gender`، `via_invite: true`) → الخروج → **إعادة الدخول بالإيميل وكلمة المرور** — كلها نجحت. وتنظيف المستخدمين/الأكواد التجريبية من القاعدة. البيانات المنشورة تصل للطلاب فوراً عبر GitHub Pages.

**الملفات المعدلة:**
- `chat/supabase/migrations/20260901000000_add_access_codes.sql` — جدول الدوال + دوال الأكواد (جديد)
- `chat/supabase/migrations/20260902000000_add_via_invite_and_gender.sql` — `via_invite` + إلزام الجنس + تحديث `handle_new_user`
- `chat/supabase/functions/invite-signup/index.ts` — دالة إنشاء الحساب برمز الدعوة (جديد)

- `chat/src/pages/Admin.tsx` — لوحة إدارة الأكواد + شارة "عبر رمز الدعوة"

- `chat/src/components/GenderOnboardingDialog.tsx` و `chat/src/contexts/AuthContext.tsx` — إلزام الجنس مع مستخدم الرمز
- `sw.js` — إصلاح توجيه SPA + كاش v24

**القاعدة:** migration الجديدة تُطبَّق تلقائياً عبر `supabase db push` (أو يدوياً من SQL Editor).

### 2026-08-20 (إصلاحات قنوات الجميع + trigger الجنس + استرجاع الجلسة — v1.3.1)

**المشاكل المُصلحة:**

1. **`can_see_channel('all')` كانت ترجع false دائماً**
   - الدالة كانت تقارن `gender = 'all'` وهذا الشرط دائماً false
   - الحل: تمت إضافة فحص صريح `_channel = 'all'` يرجع true للجميع

2. **`set_post_channel()` trigger من chat20.sql كانت تفرض قناة الجنس على المستخدمين العاديين**
   - السطر `NEW.channel := author_gender` كان يغير قناة المنشور حتى لو المستخدم اختار "الجميع"
   - الحل: `DROP TRIGGER set_posts_channel ON posts; DROP FUNCTION set_post_channel() CASCADE;`

3. **	CHECK constraint على `posts` يسمح فقط بـ `('male', 'female')`**
   - المنشورات بقناة 'all' و '09' و '10' كانت تفشل بالإدراج
   - الحل: تحديث الـ CHECK constraint إلى `('all', 'male', 'female', '09', '10')`

4. **السياسات القديمة من chat20.sql كانت تمنع النشر/اللايك/التعليقات على الجميع**
   - سياسات INSERT/SELECT القديمة كانت تمنع المستخدمين العاديين من التفاعل مع تبويب الجميع
   - الحل: حذف كل السياسات القديمة وإعادة إنشائها مفتوحة للجميع

5. **المنشورات القديمة بدون قناة (channel=NULL) لم تكن تظهر في تبويب الجميع**
   - فلتر القناة في `Chat.tsx` كان يتحقق فقط من `p.channel === "all"` ويتخطى null
   - الحل: إضافة فحص `|| p.channel === null` لعرض المنشورات القديمة

6. **فصل مفاجئ من الإداره عند فشل تجديد الـ token**
   - `onAuthStateChange` كان يحذف كل حالة المستخدم فوراً عند `SIGNED_OUT`
   - الحل: إضافة grace period ثانيتين مع إعادة محاولة `getSession()` قبل الحذف
