مشروع تخفيف الحمل على قاعدة Supabase (لاyer 1 + Layer 2 + Layer 3) — سبتمبر 2026

1) المشكلة

كانت الواجهة تقرأ من القاعدة قراءات متكررة ومتزامنة عبر كل أجهزة المستخدمين: إعدادات القنوات وأقفال الأقسام والكلمات المحظورة تُطلب مئات المرات في الساعة لكل جهاز، إضافة إلى اتصالات Realtime دائمة لكل تبويب، واستطلاعات دورية مجدولة. النتيجة: استنزاف حصة Egress وطلبات REST في Supabase.

2) الحل — ثلاث طبقات

Layer 1 — كاش المتصفح + إبطال جدولي

محلّي Frontend
  • قراءات مشتركة تخزَّن في المتصفح (ذاكرة + localStorage) بمدد: إعدادات/أقفال = ساعة بدون بوابة أو 60 ثانية معها، كلمات محظورة = ساعة/دقيقتان، معرّفات الأدمن = ساعة.
  • إبطال مستقل لكل جدول (ملف جديد src/lib/invalidation.ts): أي كتابة تُبطل كاش الجدول المتأثر فقط — لا مسح شامل.
  • إزالة كل Realtime وكل الاستطلاعات الدورية، واستبدالها بجلب عند الدخول/عودة التبويب + زر تحديث يدوي لكل قسم.
  • تقليص select("*") في مسارات الإدارة لأعمدة محدودة.

Layer 2 — بوابة القراءة (Cloudflare Worker + KV)

على السحابة madarik-chat-cache.abdalrhmanmaaith1.workers.dev
  • بيانات عامة (إعدادات/أقفال/كلمات/جولات) تُقرأ من القاعدة مرة واحدة ويوزّعها KV على كل الأجهزة — بدل ارتفاع طلبات المتصفحات.
  • /feed يُقرأ بصلاحيات المستخدم نفسه (JWT) مع كاش مقسّم لكل حساب.
  • إبطال منطقي بالـ stamp: أي كتابة تُراسل POST /invalidate فيُرفع stamp مجموعة الجدول؛ أي قيمة كاش بستامب أقدم تُعاد قراءتها — بلا حذف مفاتيح (يحترم حصة KV).
  • /metrics يحسب كل بايت وطلب خرج من البوابة ووصل للعملاء، ويُصفّى لـ KV كل 5 دقائق.
  • عند تعطّل البوابة أو إفراغ الرابط تعود كل القراءات إلى Supabase مباشرة (لا تغيير في السلوك).

Layer 3 — فهارس قاعدة البيانات

قاعدة البيانات

Migration بأربعة فهارس آمنة للتكرار (IF NOT EXISTS) لدعم الاستعلامات الساخنة: تعليقات كل منشور، منشورات مستخدم، مواعيد الجلسات، ومرشّحات المراجعة: 

CREATE INDEX IF NOT EXISTS idx_comments_post_id_created
  ON public.comments (post_id, created_at ASC);

CREATE INDEX IF NOT EXISTS idx_posts_user_id_created
  ON public.posts (user_id, created_at DESC)
  WHERE deleted_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_study_rounds_starts_at
  ON public.study_rounds (starts_at DESC);

CREATE INDEX IF NOT EXISTS idx_posts_status_created
  ON public.posts (status, created_at DESC);

يُنفَّذ من لوحة Supabase → SQL Editor (أو supabase db push).

7) الأثر المتوقع

  • إعدادات/أقفال/كلمات: من ~400 طلب/ساعة/جهاز إلى طلب واحد مشترك مخزّن كل ساعة.
  • Realtime: من اتصال دائم لكل تبويب إلى صفر اتصالات.
  • استطلاعات الصفحات: من 60–120 طلب/ساعة/تبويب إلى 1–2 عند الفتح/التركيز.
  • الإبطال: من مسح كامل الكاش إلى رفع stamp مجموعة واحدة.
  • انخفاض إجمالي Egress المتوقع: 60–75% (يُقاس من لوحة Supabase → Usage بعد 48 ساعة).

8) الإرجاع الفوري (Rollback)

أفرغ الرابط في chat/src/config/worker-config.ts:

export const READ_GATEWAY_URL = "";
