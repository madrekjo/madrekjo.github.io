# دليل بنية الدردشة — نظام تخفيف الحمل على قاعدة Supabase (الطبقات الثلاث)

> دليل شامل يشرح المشكلة، والطبقات الثلاث المنفّذة، وكيف تتدفق البيانات،
> وكيف تُنشر وتُراقب. الهدف النهائي: خفض استهلاك الـ Egress من قاعدة
> Supabase (كان يتجاوز **15 جيجابايت شهرياً**) دون المساس بالأمان أو السلوك.

---

## 1) المشكلة الأصلية

كان التطبيق (Vite + React + TypeScript على Supabase) يقرأ قاعدة البيانات
مباشرةً من كل جهاز/صفحة/مكوّن، فكانت نفس الطلبات تتكرر مئات المرات:

- `channel_settings` تُقرأ **134 مرة**، `section_locks` مئات المرات،
  `banned_words` **133 مرة**، `role_permissions` 24 مرة، وكل صفحة فيد
  تكوّن 4–5 استعلامات (منشورات + تفاعلات + تعليقات + تفاعلات تعليقات).
- حصيلة ذلك: قراءات مكرّرة عشوائية وضخمة → **Egress يتجاوز 15GB شهرياً**.

الحل: طبقات تخزين وسيط/تجميع تمنع تكرار القراءات من القاعدة وتقتربها.

## 2) نظرة عامة على الطبقات الثلاث

```
┌────────────────────────── المتصفح ──────────────────────────┐
│  Layer 1: كاش ذاكرة المتصفح (TLT + Single-flight + Poll ذكي) │
└──────────────┬───────────────────────────────────────────────┘
               │ (عند انتهاء TTL فقط تخرج طلبات)
┌──────────────▼───────────────────────────────────────────────┐
│  Layer 2: بوابة قراءة فوق Cloudflare (Worker + KV)           │
│  - البيانات العامة: قراءة واحدة تُوزَّع على كل الأجهزة        │
│  - /feed: قراءة بصلاحيات RLS الخاصة بكل مستخدم (JWT)          │
└──────────────┬───────────────────────────────────────────────┘
               │ (الطلبات الضرورية فقط)
┌──────────────▼───────────────────────────────────────────────┐
│  Layer 3: قاعدة البيانات                                    │
│  - فهارس داعمة للاستعلامات الساخنة                            │
│  - دوال RPC + قواعد RLS (منهجية الأمان)                      │
└──────────────────────────────────────────────────────────────┘
```

**الفكرة الجوهرية:** بدل «كل جهاز يقرأ كل شيء»، يقرأ الوسطاء مرة واحدة
بمهلة صلاحية قصيرة، ويُلغى الكاش فوراً عند أي تعديل إداري — فيتحقق التوازن:
**سرعة انعكاس التعديلات (بضع ثوانٍ) + خفض جذري في الطلبات والبايتات القادمة
من Supabase** (لأن البايتات التي يستهلكها المتصفح تخرج الآن من Cloudflare،
لا من القاعدة).

## 3) Layer 1 — كاش المتصفح (البطاقة الذكية)

### الملفات

| الملف | الدور |
|---|---|
| `chat/src/lib/dataLayer.ts` | المحرك الأساسي: `cachedRead` + `useSmartPoll` + Single-flight |
| `chat/src/lib/appCache.ts` | كاش «config» المشترك: قناوة القنوات، أقفال الأقسام، `admin_ids` |
| `chat/src/lib/bannedWords.ts` | كاش الكلمات المحظورة |
| `chat/src/lib/readGateway.ts` | العميل الذي يتصل ببوابة Layer 2 (مع Fallback) |
| `chat/src/contexts/AuthContext.tsx` | كاش `profiles` و `user_roles` للمستخدم |
| `chat/src/config/worker-config.ts` | عنوان البوابة (فعّلها هنا) |

### الآليات

1. **`cachedRead`** — قراءة تذهب للقاعدة مرة واحدة ثم تُقرأ من الذاكرة حتى
   نهاية `ttlMs`.
2. **Single-flight** — إن طُلب نفس المفتاح من أكثر من مكوّن في نفس اللحظة
   ينتظر الجميع وعدَ القراءة الأولى بدل تكرارها.
3. **`persist`** — يخزّن القيمة في `localStorage` فتبقى صالحة بعد إعادة
   تحميل الصفحة (إغلاق المزيد من الطلبات عند كل فتح).
4. **`useSmartPoll`** — استطلاع يعرف حالة التبويب: يتوقف عند إخفائه
   ويحدّث فوراً عند العودة إليه.
5. **الإبطال الفوري (Invalidation)** — الدوال المنفّذة:

| الدالة/الموقع | ماذا تُبطل |
|---|---|
| `Admin.tsx` (تبديل قناة/قفل قسم/كلمات) | `channel_settings`/`section_locks`/`banned_words` فوراً |
| `RolesDialog.tsx` | إعدادات القنوات + رتب المستخدم الهدف `auth:roles:{uid}` |
| `PermissionsPanel.tsx` | صلاحيات `role_permissions` + بروفايل المدير |
| `UserActionsDialog.tsx` | بروفايل + رتب المستخدم الهدف (حظر/تسجيل/اسم...) |
| `bannedWords.ts` + `invalidateAppConfig` | كلمة محظورة جديدة/محذوفة |

### عداد TTL الفعلية (المصدر الحالي)

| البيانات | TTL | موقع الضبط |
|---|---|---|
| `profiles` / `user_roles` (المستخدم) | **60 ثانية** | `AuthContext.tsx:196,212` |
| `channel_settings` / `section_locks` | 60 ثانية مع البوابة · ساعة احتياط | `appCache.ts:65` |
| `banned_words` | دقيقتان مع البوابة · ساعة احتياط | `bannedWords.ts:10` |
| `admin_ids` | **ساعة كاملة** | `appCache.ts:138` |
| فيد /feed (في البوابة) | 15 ثانية | `chat-worker.js`: TTL.feed |
| إعدادات/أقفال (في البوابة) | 60 ثانية | `chat-worker.js`: TTL.config |
| كلمات محظورة (في البوابة) | 120 ثانية | `chat-worker.js`: TTL.bannedWords |

## 4) Layer 2 — بوابة القراءة (Cloudflare Worker + KV)

### الموقع
`chat-worker/` (`wrangler.toml` + `chat-worker.js`)، يُنشر بـ `wrangler deploy`.

### النقاط (Endpoints)

| النقطة | الوصول | البيانات |
|---|---|---|
| `/health` | عام | فحص الحالة |
| `/config` | عام (مفتاح خدمة) | خريطة القنوات المفتوحة + أقفال الأقسام |
| `/banned_words` | عام (مفتاح خدمة) | قائمة الكلمات المحظورة |
| `/rounds` | *(غير موصول بالشاشات حالياً)* | الجلسات — **يوصى بمعالجته كـ /feed لاحقاً** |
| `/feed` | **مخصّص (JWT المستخدم إلزامي)** | الفيد: منشورات + تعليقات + تفاعلات + ملفات |

### كيف يعمل `/feed` بأمان؟

1. المتصفح يرسل `Authorization: Bearer <access_token المستخدم>`.
2. البوابة ترفض الطلب بـ **401** إن غاب الرمز — **مفتاح الخدمة محظور هنا**.
3. تمرّر البوابة الرمز نفسه إلى PostgREST في كل قراءة
   (`posts`, `comments`, `likes`, `comment_likes`, `profiles`) →
   **تطبَّق RLS بصلاحية المستخدم نفسه** تماماً كأنه يقرأ مباشرةً من التطبيق.
4. **الكاش مُقسَّم لكل مستخدم** بمفتاح `SHA-256` للترويسة
   (`feed:{hash}:p{page}:n{limit}:c{channel}`) — فلا يُقدَّم حساب أبداً
   نتيجة RLS خاصة بحساب آخر.
5. `channel` يمر عبر **قائمة بيضاء** (`all/male/female/09/10/11`) لمنع
   حقن عوامل PostgREST.

### البيانات العامة (بدون حاجة لـ RLS)

`/config` و `/banned_words` (و `/rounds` حالياً) تُقرأ بمفتاح الخدمة مرة
واحدة وتُوزَّع عبر KV على كل الأجهزة — هذا مقصود، فهي إعدادات عامة.

### مزامنة التعديلات الإدارية

- التعديل في لوحة الإدارة يستدعي `invalidateAppConfig()` +
  `invalidateBannedWords()` في المتصفح.
- المتصفح يطلب البوابة بالمعامل `?force=1` عند الحاجة → البوابة تعيد
  القراءة من القاعدة فوراً وتحدّث KV.
- مهلة أمان: **4 ثوانٍ** داخل `readGateway` مع Fallback تلقائي.

### Fallback (السلوك القديم المحفوظ)

- `readGateway` ترجع `null` عند أي فشل (رابط فارغ، مهلة، خطأ، رمز منتهي).
- كل متصل (مثل `fetchPosts` في `Chat.tsx`) إن لم يتلقَّ رداً صالحاً
  **يعمل المسار المباشر القديم إلى Supabase حرفياً** — لا انقطاع أبداً.

### CORS
`config/chat-worker.js`: `Access-Control-Allow-Headers` يتضمن `Authorization`
ومعامل `ALLOWED_ORIGINS` يقصره على نطاقك. افتراضياً
`https://madrekjo.github.io`.

## 5) طبقة Layer 3 — قاعدة البيانات

### الملف: `supabase/migrations/20260905000000_reduce_supabase_load.sql`

فهارس داعمة، كلها `IF NOT EXISTS` (آمنة للإعادة، لا تغيّر البنية):

| الفهرس | يدعم |
|---|---|
| `idx_comments_post_id_created` | تعليقات كل منشور في الفيد |
| `idx_posts_user_id_created` (جزئي حيث غير محذوف) | منشورات مستخدم واحد |
| `idx_study_rounds_starts_at` | الجلسات القريبة من الآن |
| `idx_posts_status_created` | تصفيات لوحة الإدارة بقيد المراجعة |

**التطبيق:** في SQL Editor سجل عبارات الملف، أو عبر CLI
(`supabase db push`). لا يوجد تغيير هيكلي.

### RLS
هي نظام الصلاحيات نفسه في Supabase — التعديلات الأخيرة جعلت /feed يمر عبرها
(بدل المرور بتجاوز مفتاح الخدمة).

## 6) تدفق طلب فيد كامل (مثال)

```
مستخدم يفتح الدردشة
   │
   ▼ Chat.tsx: fetchPosts(0)
   │
   ├─ router: البوابة مفعّلة والرمز موجود؟
   │      نعم ──► GET /feed?page=1&limit=20&channel=all
   │                مع Authorization: Bearer <JWT>
   │                │
   │                ▼ Worker
   │                ├─ tokenHash(JWT) → مفتاح KV الخاص بالمستخدم
   │                ├─ كاش موجود وصالح (15 ثانية)؟ ── نعم → يردّ فوراً
   │                └─ لا ──► PostgREST بصلاحيات المستخدم (RLS)
   │                            ├─ posts (deleted_at null + قناة)
   │                            ├─ comments + likes + comment_likes (دفعات in.)
   │                            └─ profiles (أعمدة عامة فقط)
   │                          └─ يخزّن في KV ويستجيب
   │      ← رد JSON → Chat.tsx يعيد بناء Post[] (نفس الشكل القديم)
   │
   └─ لا (بوابة معطلة / لا رمز) ──► loadDirect(): الاستعلامات المباشرة القديمة
```

## 7) الأمان — نقاط لا يجوز المساس بها

1. **مفتاح الخدمة** محظور في `/feed`؛ غياب الرمز = `401`.
2. **مدى الطلب** الوحيد للرؤية هو RLS عبر JWT المستخدم.
3. **تقسيم الكاش لكل مستخدم** في `/feed` (hash للترويسة).
4. **لا تُرسل بيانات شفهية** (توكن، مفاتيح) إلى أي جهة خارج نطاقك؛
   الصدور `CORS` + `ALLOWED_ORIGINS`.
5. `channel` عبر القائمة البيضاء. `apikey` يبقى مفتاح المشروع بينما الدور
   يُؤخذ من `Authorization` — وهذا ما يفعّل RLS.
6. لا تُضمّن مفاتيح في Git (مهمل عبر `.gitignore`).

## 8) النشر

### أولاً: بوابة Layer 2 (مرة)
```bash
cd chat-worker
wrangler kv namespace create CHAT_KV        # إن وُجد id في wrangler.toml فهذا جاهز
wrangler secret put CHAT_SERVICE_KEY        # مفتاح خدمة Supabase
# اختياري: wrangler secret put ALLOWED_ORIGINS -> https://madrekjo.github.io,http://localhost:5173
wrangler deploy                             # يطبع عنوان URL
```
ثم ضع العنوان في `chat/src/config/worker-config.ts`. عند تغيير الكود
لاحقاً: `npx wrangler deploy` فقط.

### ثانياً: الفرانت (كل تحديث)
```bash
cd chat
npm run build            # يبني ويوزّع المخرجات داخل المجلد الجاهز للموقع
git add -A && git commit -m "..." && git push origin main
```

### ثالثاً: قاعدة البيانات (مرة)
سجّل محتوى `chat/supabase/migrations/20260905000000_reduce_supabase_load.sql`
في Supabase → SQL Editor، أو `supabase db push`.

## 10) توصيات مستقبلية (أثر إضافي)

1. **ربط `/rounds`** بنفس أسلوب `/feed` (JWT + كاش لكل مستخدم) قبل وصله
   بأي شاشة — حالياً غير موصول والمسار بلا ضرر.
2. **أرشفة `admin_actions`** شهرياً لضبط الحجم:
   ```sql
   DELETE FROM public.admin_actions WHERE created_at < now() - interval '90 days';
   ```
3. **ضبط `KNOWN_CHANNELS`** في `chat-worker.js` عند إضافة قناة جديدة.
4. مراقبة حدود **Cloudflare KV** (قراءات/كتابات) — الكاش لكل مستخدم في /feed
   يزيد عدد المفاتيح كتابةً كل 15 ثانية لكل حساب نشط.
